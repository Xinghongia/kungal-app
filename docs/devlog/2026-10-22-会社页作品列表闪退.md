# 2026-10-22 · 修复会社/发行商页闪退（0.8.20）

## 背景

驾驶员实机反馈两条路径都会闪退：

1. 我的 → 个人主页 → 动态里的评分 → 查看作品资料 → 作品信息里的会社/开发商/发行商；
2. 搜索 → 游戏 → 会社或发行商。

两条路径最终都进入 App 内会社详情页。

## 根因

`GET /api/v1/companies/{id}/works` 的元素是 `company_work` 包裹：

```json
{"object":"company_work","work_summary":{...},"via_company":null}
```

而 `core/.../GalgameEntityApi.kt` 的 `companyWorks` 直接按普通作品列表
（`PagedList<WorkSummary>`）解析。`ignoreUnknownKeys` 让解析不报错，但每条作品的
`id` 全部落成空字符串，`PagedListContent` 把它们作为 LazyColumn 的 key，
触发 `IllegalArgumentException: Key "" was already used`，界面直接崩溃。

官方 OpenAPI 中该接口的响应类型确认为 `PageListCompanyWork`；标签、引擎、系列的
作品列表接口都返回普通 `work`，只有会社是特例。

崩溃现场从设备 dropbox 取得：`data_app_crash` 2026-10-22 14:46:59 / 14:47:33，
`Process: com.kungal.app v48 (0.8.19)`，堆栈为 LazyColumn 测量阶段的 key 冲突。

## 修复

- `companyWorks` 改为按 `PagedList<CompanyWork>` 解析，会社详情页取
  `work_summary` 转成作品列表后再交给通用列表；`via_company` 保留在模型里备用。
- `PagedListContent` 增加 key 兜底：接口给出空 id 或重复 id 时，逐项退回本地下标
  key，避免同类数据问题把整页打崩。
- 新增真实响应 fixture `galgame_company_works.json`（会社 15268，含
  `via_company` 有值/无值两种情况），单测同时断言包裹结构与拆包结果。

## 0.8.20 的回归与 0.8.21 修正

驾驶员装机 0.8.20 后复测仍闪退。设备 dropbox 15:03:18 记录显示是**新引入的**问题：

```
java.lang.IndexOutOfBoundsException: Index: 0, Size: 0
  at PagedListContentKt.PagedListContent$lambda$...$2(PagedListContent.kt:189)
  at ...NearestRangeKeyIndexMap.<init>
```

`itemKeys` 用 `remember(items)` 在父组合里生成，而 LazyColumn 的 item provider 是子组合，
会在父组合刷新之前就带着新的 items 数量重建 key 索引；此时 `itemKeys` 还是空列表，
key 回调里的 `itemKeys[index]` 直接越界。这是 0.8.20 新增 key 兜底时写出的索引访问 bug。

修正：key 的查询改为 `pageItemKeyAt(keys, index)`，列表落后时按下标兜底，
不再越界；两个纯函数（`pageItemKeys` / `pageItemKeyAt`）提出组件并补 6 项单测，
其中一项专门复现「items 已有 3 项、key 列表还是空」的现场。
